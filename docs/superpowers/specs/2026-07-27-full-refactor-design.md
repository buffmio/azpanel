# azpanel 全面重构设计

## 1. 目标

在保留 ThinkPHP 8 服务端渲染模式的前提下，全面重构 azpanel 的内部结构、页面模板、交互代码、设计系统和 Docker 部署方式。

重构必须满足以下可观察结果：

- 保留现有业务功能、URL、HTTP 方法、请求字段、响应字段和权限语义。
- 现有数据库可直接升级，不要求用户清空数据或执行破坏性迁移。
- 用户端、认证页面和管理后台采用统一的轻量 SaaS 视觉语言。
- 每个业务模块可独立迁移、验证和回滚。
- Docker 部署可复现、可升级、可备份、可恢复。

## 2. 范围

### 2.1 保留的功能

功能基线以 `feature/docker-deployment` 分支当前行为为准，包括：

- 登录、退出、注册、验证码和密码重置。
- 用户概览、个人资料、通知偏好、密码、SSH 密钥和自动刷新配置。
- 登录记录、账户分享、回收站、使用文档和开源协议。
- Azure 账户的创建、查询、编辑、分享、刷新、配额、费用和资源组管理。
- Azure 虚拟机的创建、查看、搜索、刷新、同步、启停、重启、升降配、磁盘操作、重装、凭据重置、防火墙、流量图表、备注、删除和销毁。
- 流量控制规则、执行状态和日志。
- 后台概览、用户、公告、站点设置、邮件、Telegram、域名解析和各类审计日志。
- 当前分支中可达的云厂商、代理、通知、定时任务和运维能力。
- Docker 安装、重新部署、HTTPS、证书续签、数据库备份、卸载和彻底清理。

实现前必须把上述项目细化为可执行的功能矩阵，并以现有代码和运行行为补齐隐式入口。

### 2.2 不在本次范围

- 不改为 Vue、React 或其他单页应用。
- 不建立新的公共 API 版本。
- 不重新设计业务规则、计费逻辑或云资源生命周期。
- 不在首期交付深色主题；设计 Token 需允许后续增加。
- 不为未来需求建立当前业务不需要的插件系统或微服务。

## 3. 兼容性边界

以下内容视为外部契约，重构期间保持兼容：

- 路由路径、HTTP 方法和认证要求。
- 表单与 JSON 请求字段。
- JSON 响应中的现有字段、状态含义及主要错误语义。
- 数据表、现有字段及其中的生产数据。
- `.env` 中仍在使用的配置键。
- Docker 数据卷、证书、备份和无损重新部署行为。

数据库变更只允许向后兼容的增量迁移，例如新增表、可空字段或索引。需要替换旧结构时，先双写或迁移数据，验证完成后再在后续版本删除旧结构。

## 4. 目标架构

应用继续采用 ThinkPHP 单体架构，并按职责分层：

1. `Controller` 处理路由、鉴权、请求调用和兼容响应，不承载云资源业务流程。
2. `Request` 或等价验证单元负责输入规范化与校验。
3. `Application Service` 表达用户可见的业务用例，定义事务和长任务边界。
4. 领域模型及仓储负责业务状态和持久化。
5. Azure、其他云厂商、邮件、Telegram、代理与任务执行通过独立基础设施客户端接入。
6. `View` 负责服务端页面组合，不直接实现业务规则。

依赖方向为：

`HTTP 请求 → Controller/Request → Application Service → Domain/Infrastructure → View 或兼容 JSON 响应`

Controller 将统一的成功结果和领域异常转换为现有响应格式。基础设施代码不得依赖模板或 HTTP 请求对象。

## 5. 服务端模板与前端结构

### 5.1 页面外壳

建立三个外壳：

- 认证外壳：登录、注册和密码重置。
- 用户外壳：用户概览、云账户、虚拟机、流量控制和个人功能。
- 管理外壳：系统设置、用户、公告和日志。

用户外壳与管理外壳共享品牌、设计 Token、基础组件和交互模块，但保持不同的导航信息架构。

### 5.2 模板组件

提取具有明确输入和单一职责的服务端模板组件：

- 页面标题、面包屑和操作区。
- 按钮、输入框、选择器、复选框和字段错误。
- 卡片、摘要指标、状态徽章和描述列表。
- 数据表格、移动端资源卡片、筛选器和分页。
- 空状态、加载状态、页面级错误和权限受限状态。
- Toast、确认弹窗、危险操作弹窗和任务进度。
- 代码块、复制按钮和图表容器。

业务页面组合这些组件，不复制样式和通用交互。组件接口以明确参数为主，避免读取不可见的全局变量。

### 5.3 浏览器代码

移除页面中重复的内联 AJAX 逻辑，改用原生 ES Modules：

- 请求客户端统一处理 CSRF、超时、JSON 解析、登录过期和兼容错误。
- 表单模块负责提交状态、字段错误和防止重复提交。
- 弹窗模块负责确认、危险资源名称和焦点管理。
- 任务模块负责轮询、进度、完成状态和可追踪任务编号。
- 页面模块只绑定当前页面的业务动作。

在对应模块完成迁移并通过回归前保留 jQuery/MDUI；所有页面迁移完成后再删除旧依赖。

## 6. 视觉与交互设计

采用已确认的“轻量 SaaS 控制台”方向：

- 浅色背景、白色内容面、蓝色主操作色和语义状态色。
- 8px 间距体系、统一圆角、轻边框与克制阴影。
- 桌面端采用固定侧栏与顶部环境栏。
- 页面统一为标题区、摘要区、筛选区、主体内容和危险操作区。
- 平板折叠侧栏；手机使用抽屉导航，宽表格转换为资源卡片或允许有提示的横向滚动。

设计 Token 至少覆盖颜色、字体、间距、圆角、阴影、层级、断点和动效。组件状态覆盖默认、悬停、焦点、禁用、加载、成功、警告和错误。

可访问性要求包括语义化 HTML、可见焦点、键盘操作、表单标签、非纯颜色状态表达、弹窗焦点约束，以及满足常规正文可读性的颜色对比度。

## 7. 数据流与错误处理

- 页面导航和完整表单默认由服务端渲染。
- 搜索、筛选、状态切换、批量操作和任务进度可继续使用现有 JSON 请求。
- 校验错误显示在对应字段旁，并保留用户输入。
- 短暂成功或一般失败使用 Toast。
- 阻止页面继续操作的错误使用页面级提示。
- 长任务展示当前阶段、最终结果和任务编号。
- 会话过期统一引导重新登录，并尽量保留当前返回地址。

创建、删除、重装、磁盘交换、防火墙和凭据操作必须保留现有幂等、补偿和回滚语义。危险操作需要二次确认，并明确显示资源名称和不可逆影响。

## 8. 安全要求

- 所有状态变更请求执行 CSRF 校验。
- 模板默认转义；富文本只允许经过白名单净化的内容。
- 权限检查在服务端执行，隐藏按钮不能代替授权。
- 凭据、Token、数据库密码和证书私钥不得写入应用日志。
- 配置与日志界面对敏感值脱敏。
- 文件路径、代理地址和云资源标识在进入基础设施层前完成校验。
- Docker 容器采用满足运行需要的最小权限，应用进程不以 root 身份提供请求服务。

## 9. Docker 与运维

保留 Nginx、PHP 应用和 MariaDB 的服务边界，并改进：

- 使用可锁定依赖的多阶段构建，避免生产容器在启动时安装依赖。
- 添加应用与 Web 健康检查，并以健康状态控制依赖启动。
- 明确代码、运行目录、数据库、证书和备份的持久化边界。
- 保留现有 `.env` 与数据卷的升级路径。
- 安装、重新部署、备份、恢复、证书续签、卸载和清理均可重复执行并给出明确错误。
- 文档提供升级前备份、升级验证和回滚步骤。

彻底清理仍必须显式确认，且不得删除源代码或 Git 历史。

## 10. 渐进迁移顺序

迁移按纵向业务切片执行：

1. 建立功能矩阵、兼容契约测试和测试基座。
2. 建立设计 Token、模板组件、请求客户端和三个页面外壳。
3. 迁移认证流程。
4. 迁移用户概览、资料、登录记录、分享和回收站。
5. 迁移 Azure 账户及资源组。
6. 迁移 Azure 虚拟机及所有资源操作。
7. 迁移流量控制、任务进度和图表。
8. 迁移管理后台。
9. 整理其他云厂商、通知、代理和定时任务边界。
10. 重构 Docker 构建、部署与恢复流程。
11. 删除已经没有调用方的 MDUI、jQuery、重复模板和旧业务实现。

每个切片遵循：

`锁定旧行为 → 重构后端 → 替换 UI → 自动化回归 → 人工核对关键路径 → 删除该切片旧实现`

不得在未完成回归时同时删除旧实现。

## 11. 测试与验收

测试体系包括：

- Application Service 和领域规则单元测试。
- Controller、权限、校验和兼容响应集成测试。
- 数据库迁移及已有数据升级测试。
- 模板渲染、转义和关键组件状态测试。
- 登录、云账户、虚拟机、流量控制和管理后台的浏览器冒烟测试。
- Azure 等外部系统的适配器契约测试，默认使用受控替身，真实环境测试单独执行。
- Docker Compose 配置、镜像构建、健康检查、首次安装、重新部署、备份恢复和回滚验证。

每个切片至少通过项目测试、PHPStan、模板/前端静态检查和相关浏览器流程。最终验收要求：

- 功能矩阵全部通过。
- 公开兼容契约无非计划变更。
- 现有数据库和部署配置可直接升级。
- 桌面与手机关键流程可用。
- 危险云操作的失败、超时和回滚路径经过验证。
- 部署、升级、备份、恢复和回滚文档完整且已实际演练。

## 12. 风险控制

- 以功能矩阵防止“页面看起来完成但隐式功能丢失”。
- 以兼容测试约束路由和响应变化。
- 以业务切片限制同时变动范围。
- 外部云操作通过适配器和受控替身测试，避免测试误操作真实资源。
- 数据库与部署变更在包含真实旧数据副本的临时环境验证。
- 每个阶段保持可运行版本和明确回滚点。
